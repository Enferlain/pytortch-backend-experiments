## PyTorch boundaries
- [inductor backend registration](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_dynamo/backends/inductor.py): registered Dynamo backend imports and calls `compile_fx`. A Dynamo backend consumes captured FX; implementing one is different from replacing Inductor device codegen.
- [compile_fx](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/compile_fx.py): inspect `compile_fx`, its forward/backward callbacks and invocation of `dynamo_common.aot_autograd`; separate its AOT export path and caches. [AOTAutograd implementation](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_functorch/aot_autograd.py) supplies tracing/partitioning machinery. Establish which path runs for inference/training and backward.
- [GraphLowering](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/graph.py), [lowering registry](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/lowering.py), [Inductor IR](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/ir.py): trace ATen overload → decomposition/lowering → loop/buffer/external representations. For add, `add = register_pointwise(aten.add, ...)` includes alpha and boolean handling. Do not assume the Python call is still one addition at this boundary.
- [Scheduler](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/scheduler.py): fusion/dependencies and `create_backend` / `get_backend`. [DeviceCodegen and register_backend_for_device](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/codegen/common.py): scheduling/wrapper registration and `init_backend_registration`. Private interfaces are version-sensitive; verify initialization order and replacement effects.
- [CUDACombinedScheduling](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/codegen/cuda_combined_scheduling.py): delegates among Triton and multiple template schedulers; `choose_node_backend` is a useful boundary. [TritonScheduling](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/codegen/triton.py) implements the Triton path. External/library calls and templates need not use this path.
- At this snapshot, default backend initialization imports Triton scheduling and `Scheduler.create_backend` checks `has_triton()` for GPU routes other than MPS. A registered CubeCL scheduler alone does not demonstrate Triton-free execution. Investigate imports, templates, async compilation and runtime dependencies too. [AsyncCompile](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/torch/_inductor/async_compile.py) is another boundary to inspect.
- Tests: [TestDebugTrace.test_debug_trace](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/test/inductor/test_debug_trace.py) establishes emitted trace artifacts; [Inductor behavior tests](https://github.com/pytorch/pytorch/blob/60de3b7f3316d28ab80fb8029742e201d5c6ab7b/test/inductor/test_torchinductor.py) gives operation/shape cases. Test coverage is not a complete semantic contract.

## CubeCL and Pliron
- [CubeCL dependencies](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/Cargo.toml) uses Pliron/pliron-llvm 0.19 and LLVM bindings/bundler. Upstream Pliron HEAD is separately inspected; it is not proof of the exact version resolved in a user's lockfile.
- [cubecl-ir](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-ir/src/lib.rs) exports Pliron infrastructure; [Scope](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-ir/src/scope.rs) owns context/module state. CubeCL dialect operations are built in that infrastructure. “CubeCL IR → Pliron” must not be drawn as an obligatory additional unrelated IR.
- [math dialect](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-ir/src/dialect/math.rs), [SimplifyOpsPass / CanonicalizePass](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-ir/src/rewrite.rs), [InstCombinePass](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-opt/src/passes/inst_combine.rs) separate operation-level folding/rewrite interfaces and optimization passes. Trace macro expansion and actual pass assembly.
- [Compiler trait](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-runtime/src/compiler.rs) takes `KernelDefinition` and compilation options, returns associated `Representation`; inspect `compile`, `buffer_io`, `extension`, `lang_tag`. [server re-export](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-server/src/compiler/base.rs) is not a distinct compiler contract.
- [CppCompiler::compile_ir](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-cpp/src/shared/base.rs) builds a Pliron pass pipeline then emits target C++/MSL. Examples in its sequence include `SROAPass`, `ResolvePendingPass`, checked I/O, target lowering, `SCCPPass`, `InstCombinePass`, `SimplifyOpsPass` and memory/visibility work. Order/repetition matters; reread current source.
- [PlironCompiler and LLVM pipeline](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-llvm/src/shared/base.rs) uses CubeCL ops, target prologue/epilogue, `BranchToSCFPass`, `SCFToLlvmCf`, entry ABI lowering, `CubeToLLVMPass`, and conversion to LLVM IR. [LLVM target/artifact map](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-llvm/README.md) documents CPU ORC JIT, AMDGPU code object and NVPTX PTX. LLVM dialect operations represented by Pliron are distinct from native LLVM IR.
- [Pliron](https://github.com/pliron-org/pliron/blob/d7ec90818cc9793452f62f91df906e9329722198/README.md) is a Rust extensible IR framework inspired by MLIR, not MLIR itself and not NVIDIA's assembler. [Pass / Passes / OpPass / PMConfig](https://github.com/pliron-org/pliron/blob/d7ec90818cc9793452f62f91df906e9329722198/src/pass.rs) provides orchestration; [MatchRewrite](https://github.com/pliron-org/pliron/blob/d7ec90818cc9793452f62f91df906e9329722198/src/irbuild/match_rewrite.rs) and [DialectConversion](https://github.com/pliron-org/pliron/blob/d7ec90818cc9793452f62f91df906e9329722198/src/irbuild/dialect_conversion.rs) provide rewriting/conversion infrastructure. [pass tests](https://github.com/pliron-org/pliron/blob/d7ec90818cc9793452f62f91df906e9329722198/tests/pass.rs) checks this machinery. A CubeCL-supplied rewrite running under Pliron is not automatically “Pliron's optimization.”

## Actual target routes at the snapshot
| Selection | Lowering result | Runtime compilation/load boundary |
| --- | --- | --- |
| CUDA Cpp | CUDA C++ | NVRTC → PTX → CUDA driver module loading/JIT |
| CUDA Llvm | Pliron LLVM dialect → native LLVM IR → NVPTX PTX | CUDA driver module loading/JIT |
| HIP Cpp | HIP C++ | HIPRTC → code object → HIP module loading |
| HIP Llvm | Pliron LLVM dialect → native LLVM IR → AMDGPU emission/linking | linked AMD code object → HIP module loading |

Sources: [CudaBackend/CudaCompiler](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-cuda/src/compiler.rs), [HipBackend/HipCompiler](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-hip/src/compiler.rs), [CUDA finalization](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-cuda/src/compute/artifact.rs), [CUDA loading](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-cuda/src/compute/modules.rs), [HIP finalization](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-hip/src/compute/artifact.rs), [NVPTX emission](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-llvm/src/nvptx/codegen.rs), [AMDGPU emission/linking](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-llvm/src/amdgpu/codegen.rs). Both backend alternatives are compiled; at this snapshot enabling the `cpp` Cargo feature changes the default. Record the actual selection and feature unification, not presumed defaults. Do not claim CubeCL invokes offline ptxas merely because it emits PTX.

Other routes include SPIR-V/WGSL/Metal/CPU; inspect selected compiler and runtime afresh. [SPIR-V debugging](https://github.com/tracel-ai/cubecl/blob/3b47011522dbe79544388267c2b6cf8278913a8b/crates/cubecl-spirv/README.md) verifies one additional artifact route, not all portability behavior.

## Burn and Triton reference roles
Do not infer “LLVM bug” merely because preceding IR looks correct. Check IR preconditions/flags, ABI, target options, loader/runtime state and a discriminating boundary experiment before assigning downstream ownership, even when an upstream debugging guide offers that heuristic.

- [Burn CubeBackend](https://github.com/tracel-ai/burn/blob/f7de05ffc17b04bf718c2b2a51e1f415548d32e0/crates/burn-cubecl/src/lib.rs) implements Burn tensor operations using CubeCL kernels and re-exports its CubeCL dependency; runtime wrappers choose devices, fusion can wrap the backend. [custom-kernel guide](https://github.com/tracel-ai/burn/blob/f7de05ffc17b04bf718c2b2a51e1f415548d32e0/burn-book/src/advanced/backend-extension/custom-cubecl-kernel.md) demonstrates consumer integration. Burn provides useful scheduling/fusion/ABI usage examples, not an obligatory stage in a PyTorch adapter or a PyTorch semantic specification.
- [BaseBackend.add_stages](https://github.com/triton-lang/triton/blob/0bea346bfbb357072cdd16fa6ebd7afaa8a0399f/python/triton/backends/compiler.py) and [compile / CompiledKernel](https://github.com/triton-lang/triton/blob/0bea346bfbb357072cdd16fa6ebd7afaa8a0399f/python/triton/compiler/compiler.py) expose staged compilation and artifacts. [NVIDIA add_stages](https://github.com/triton-lang/triton/blob/0bea346bfbb357072cdd16fa6ebd7afaa8a0399f/third_party/nvidia/backend/compiler.py) registers ordinary Triton `ttir → ttgir → llir → ptx → cubin`; Gluon input has a different start. [AMD add_stages](https://github.com/triton-lang/triton/blob/0bea346bfbb357072cdd16fa6ebd7afaa8a0399f/third_party/amd/backend/compiler.py) has `llir → amdgcn → hsaco`. Current NVIDIA `make_cubin` invokes ptxas; do not transfer this fact to CubeCL.
